# Requirements Flow Alignment

## 適用範囲と進め方

未決の設計判断に必要な工程だけを使う。ユーザーが既に示した目的・導線・受入条件は確定事項として再利用し、確認済みの内容を承認待ちに戻さない。画面のない処理では画面モックと画面用チェックを省略し、入力・出力例や操作で確かめる。

以下の工程・テンプレートは認識合わせの道具であり、全作業の開始条件ではない。判断待ちの箇所を明記しながら、既決の範囲の現物調査、比較、実装準備を進める。依頼された実装も、必要な判断が揃っていれば同じ作業内で検証まで進める。

## 1. Mission

人間が作りたいものを、長文の応酬ではなく、**目的 → 人間の利用Flow → 画面 → データFlow → 実装差分**の順で確定する。

目標は、通常なら数時間・数日かかる認識合わせを、**人間が30分以内でレビューできる一つのチェックポイント**へ圧縮すること。

このSkillの成功は、長い仕様書を作ることではない。

成功条件：

- 一般の大人が「何のための仕組みか」を説明できる
- 人間が最初に何を見て、何を押し、何を得るかが分かる
- 画面イメージを見て修正点を具体的に指摘できる
- 現在の成果物と目標状態を混同しない
- 未決事項だけを質問できる
- 承認前の仮説を、完成基準として採点しない

---

## 2. Authority order

設計判断の優先順位は必ず次の順にする。

1. ユーザーが達成したい結果
2. ユーザーが明言した利用場面・操作
3. ユーザーが承認したFlow・画面
4. 参考スクリーンショット・他人の事例
5. 現在存在するコード・文書・フォルダ・画面・データ
6. AIの推論・好み

### General rule

> **作りたい状態が未確定なのに、現在ある成果物を完成像の基準として扱わない。**

現在あるものは「現在地の証拠」であり、「正解」ではない。

---

## 3. Six layers — never mix them

混同している点を、次の6層のうち関係する層に分ける。

| 層 | 答える問い | 例 |
|---|---|---|
| 1. Purpose | なぜ作るのか | 過去の知識を定着させたい |
| 2. Human use flow | 人間はいつ、何を見て、何をするか | Homeからカテゴリを選び読む |
| 3. Screen / output | 画面や成果物は何を見せるか | カテゴリカード、書名、Xタイトル |
| 4. Data flow | データはどこからどこへ流れるか | JSONL → Sourceノート → Base |
| 5. Processing / rules | 内部でどう処理するか | 分類表、重複判定、要約長 |
| 6. Current state | 今は何が実装済みか | 現在のHome、既存スクリプト |

### Prohibition

- Processingの細部をHuman use flowへ混ぜない
- Current stateでFlowを終わらせない
- Current stateを基準に「目標とズレている」と断定しない
- Purposeを省略して画面やコードから始めない

## 4. What counts as a Flow

### 4.1 Human use flow

次を含める。

```text
きっかけ
  ↓
人間が見る画面・成果物
  ↓
人間の操作
  ↓
見える結果
  ↓
次の操作または得たい状態
```

例外処理、文字数、ハッシュ、欠損判定などは、人間の操作を変えない限りFlowへ書かない。

### 4.2 Data flow

次を含める。

```text
入力元
  ↓
保存場所
  ↓
変換主体・処理
  ↓
出力先
  ↓
人間用表示 / AI用参照
```

抽象語だけで省略しない。分かる範囲で実体名、ファイル、フォルダ、DB、アプリ名を書く。

不明な箇所は推測せず「未確認」と書く。

### 4.3 Processing specification

次は別表に置く。

- 分類ルール
- 要約の長さ
- 欠損判定
- 再同期
- 重複排除
- エラー処理
- テスト
- 性能・コスト

## 5. 30-minute alignment protocol

人間が読む最初のチェックポイントは、一ページ相当に抑える。

### Step 1 — Material inventory

受け取った資料を、役割付きで整理する。

```text
目的を示す資料
参考UI
現在実装
過去の未承認案
外部調査
```

同じ資料をすべて同じ重みで扱わない。

### Step 2 — Purpose statement

ユーザーの言葉を使い、次の3行を作る。

```text
作る理由：
最終的に変えたい人間の状態：
成功ではないもの：
```

資料がPurposeを支えていなければ、勝手に補完せず未決とする。

### Step 3 — Concrete human scenario

抽象的な「検索・整理・活用」ではなく、一つの具体的場面を書く。

```text
いつ
何が起きて
どの画面を開き
何を選び
何を読んで
どうなるか
```

### Step 4 — One human flow

箱は原則5〜7個。一般の大人が説明なしで追える言葉にする。

Mermaidを既定にしない。ユーザーが最も速く理解・修正できる形式を選ぶ。

### Step 5 — One screen mock

画面上の操作や見え方が未決の場合、主導線の最初の1〜2画面を実際に近いデータで作る。既存画面で判断できる場合はそれを使う。

画面モックには必ず次を含める。

- 画面名
- ユーザーが最初に見るもの
- 主要操作
- クリック後の行き先
- 表示しないもの
- 実データまたは明確に「例」と表示したデータ

### Step 6 — Data flow

人間の利用Flowとは別に、入力元、保存先、変換、出力先を書く。

### Step 7 — Decision labels

すべてを次のどれかで表示する。

- `[確定]`
- `[現在実装]`
- `[提案]`
- `[未決]`

AIの提案を確定事項の文体で書かない。

### Step 8 — Questions

質問は、本当に回答がないものだけ最大3問。

各質問に次を付ける。

```text
なぜ今決める必要があるか
選択肢
決めなくても進められるか
```

既に回答済みの内容を質問し直さない。

### Step 9 — Resolve material decisions

ユーザーの判断が必要な未決の目的・導線だけを確認する。既に依頼や会話で確定した要件との比較は進めてよい。未決の案との比較は仮説として示し、独立した調査や既決範囲の作業を止めない。

AIが作った未承認の図を、ユーザーが決めた要件として扱わない。

### Step 10 — Gap and handoff

確定した要件について次を作り、未決の箇所はその状態を残す。

```text
目標状態
現在状態
再利用するもの
変更するもの
実装しないもの
受入条件
```

## 6. Screen design rules

1. 画面には一つの主要目的を持たせる。
2. Homeは、ユーザーの最初の判断を助ける。
3. 全件一覧を置く場合、その一覧を見る明確な理由が必要。
4. 数千行を表示できることと、人間が使えることを混同しない。
5. 内部ID、状態、エラー、管理Propertiesを主表示しない。
6. 人間が内容を予測できるラベル・タイトルを使う。
7. 画面モックは、フォルダ構造図の代わりではない。
8. デスクトップだけでなく、必要ならモバイルで最初の操作が可能か確認する。
9. 参考スクリーンショットは、思想・構造・操作を抽出する。外見を無批判にコピーしない。
10. 「この画面を開いた人は、次に何をするか」を各画面で答える。

---

## 7. Existing artifacts rule

既存成果物が目標と混同されている場合、必要な事実を次の2群に分ける。資料を受け取るたびに表を作り直す必要はない。

### Reusable facts

- 実際のデータ形式
- 保存場所
- 動いている取込処理
- 保護すべき原本
- 既存テスト
- 現在の制約

### Not authoritative for target design

- 現在のHome
- 仮のProperties
- 仮の分類
- デモKnowledge
- 未承認のFlow
- 別AIが作った仕様
- 現在実装が止まっている地点

現物を読んだ直後に、完成像を推測して評価しない。

---

## 8. Use of research and examples

外部事例は、次の問いへ使う。

- 未決の運用を他人はどう解いたか
- 継続できなかった理由は何か
- 画面・頻度・人間作業の選択肢は何か
- 技術的に可能か

外部事例を、ユーザーの目的の代わりにしない。

取得ツールのREADMEを「知識を活用できた成功事例」と数えない。Capture、閲覧、統合、利用、更新を区別する。

---

## 9. Response and revision budget

### First checkpoint

- 目的：5行以内
- Human use flow：一つ
- 画面モック：未決の画面がある場合のみ1〜2画面
- Data flow：主要媒体ごと
- 未決：最大3件
- 読了目安：5分以内

### Revision

ユーザーが一部分を否定した場合：

1. 否定された層を特定する
2. その層の仮説を撤回する
3. 関係する部分だけ更新する
4. 全文を最初から再生成しない
5. 同じ説明を再要求しない

謝罪や経緯説明を長文化せず、修正版を先に出す。

---

## 10. Anti-patterns

次を禁止する。

- 目的が分からないまま完成仕様を作る
- 現在実装を神様として扱う
- 未承認のFlowで「ズレ」を採点する
- 現在実装が止まった地点で完成Flowを止める
- 処理仕様を大量に書き、Flowと呼ぶ
- 抽象化し過ぎて、入力元・画面・保存先を消す
- 参考画面へ過剰適合する
- 画面の判断が必要なのに、そのイメージを示さず文章だけで要件を詰める
- Homeへ全件表を置いて「管理できる」とみなす
- ユーザーが答えたことを再質問する
- AIの好みで層、Property、DB、フォルダを追加する
- 長文を返したことを進捗とみなす
- 外部調査件数を品質の代わりにする
- ユーザーの訂正後も、古い仮説を基準にする

## 11. Decision ledger

会話が長くなる案件では、必ず短い決定台帳を維持する。

```markdown
| ID | 決定・発言 | 状態 | 根拠 | 再質問禁止 |
|---|---|---|---|---|
| D001 | Homeはカテゴリ入口 | 確定 | ユーザー明言 | yes |
| D002 | Knowledge生成単位 | 未決 | 画面確認後 | no |
```

新しい回答の前に台帳を確認する。

ユーザーが変更しない限り、`再質問禁止: yes`の内容を聞き直さない。

---

## 12. Required first deliverable

認識合わせが必要な場合、次のうち未決の判断に役立つ項目を出す。既決事項は短く参照する。

```markdown
# 1. 作る理由
# 2. 代表的な利用場面
# 3. 人間の利用Flow
# 4. 最初の画面モック
# 5. データFlow
# 6. 確定 / 提案 / 未決
# 7. 最大3問
```

現在実装の調査が判断を助ける場合は先に行ってよい。合意した目標と、現物から確認できた事実を区別する。

---

## 13. Quality gate

次のうち対象に関係する条件で実装指示を確認する。未決の判断は、確定した指示と分ける。

- [ ] Purposeがユーザーの言葉で書かれている
- [ ] 保存・検索などの手段ではなく、人間の最終状態が書かれている
- [ ] Human use flowとData flowが分かれている
- [ ] Processing仕様がFlowへ混入していない
- [ ] 最初の画面で何を見るかが分かる
- [ ] 画面上の主要操作が分かる
- [ ] 現在実装は現在地としてだけ扱われている
- [ ] 参考例は参考として扱われている
- [ ] AI推論にラベルがある
- [ ] 未決事項が明示されている
- [ ] ユーザーが既に答えたことを聞き直していない
- [ ] 受入条件が人間の操作で検証できる
- [ ] 一般の大人が説明なしで理解できる
- [ ] 読む量が必要最小限である

---

## 14. Completion contract

このSkillを使った設計作業は、次の状態で完了する。

1. Purposeがユーザーの依頼または既存の合意に根拠を持つ
2. 関係するHuman use flowの重要な未決事項が解決した
3. 画面の判断が必要な場合、ユーザーが具体的な画面を見て修正できた
4. Data flowの事実と未確認点が分かれた
5. 現在実装との比較で、確定要件と未決の仮説を区別した
6. 実装範囲と非範囲が明確
7. 受入条件が対象に応じた画面・操作・入出力・データ保全で検証可能
8. 次のAIが会話全体を読まなくても引き継げる

未決の仮説を完成仕様として扱わない。設計全体に未決が残っていても、既に確定し依頼された独立部分は実装・検証を進め、その範囲を明示する。
